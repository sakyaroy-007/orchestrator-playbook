# 审查与合并

原则是**不接受自报**。执行者说 done，不等于真的 done。审查结论里的每一条，都要有你亲手跑出来的证据。

## 审查步骤

1. **看全貌**
   ```bash
   git -C <wt> status --short                     # 必须为空
   git -C <wt> log --oneline <main>..HEAD          # 提交以卡号开头，最后一个包含 docs/changes/<卡号>.md
   git -C <wt> diff --stat <main>...HEAD           # 改了哪些文件，有没有越界
   ```
2. **复跑卡上全部验收命令**，数字对不上就退回。再跑一次全量测试；改过测试的卡，还要加跑逐个单跑和逆序跑。
3. **读完整 diff**，不能只看摘要。重点查四类问题：
   - **越界**：改了卡外的文件或共享文档，顺手重构，改了依赖
   - **假测试**：
     - 用 `skip` / `xfail`、`|| true`、`try/except: pass` 绕过失败
     - 删改断言，或者放宽比较
     - 期望值照抄实际输出
     - 测试根本没调到被测代码
   - **密钥与残留**：令牌、密码、调试打印、断点、个人绝对路径、临时文件
   - **不可逆**：迁移没有 downgrade，破坏性脚本，会丢数据的默认值
4. **核对变更说明**：每一条「已更新」「已验证」都要去看。变更说明里写了、实际没做的，本身就算必须修。
5. **高风险卡（🔴）加码**：
   - **逐行读**，对每个输入问一句「谁能控制它」，这就是信任边界。典型问题是可伪造的请求头，以及客户端自报的时长、时间、身份。
   - **事务边界**：基础件会不会顺手提交调用方还没提交的改动？失败路径会不会留下半截数据？
   - **并发与幂等**：并发测试连跑多轮；试重复请求、重放、乱序。
   - **变异检验**：故意改坏关键的一行，比如去掉锁、换掉加锁顺序、删掉校验，确认测试会变红；改回来后用 `diff` 确认已恢复原样。测试抓不住的变异就是测试缺口，按必须修处理。
6. **回报里的「发现」**：逐条决定立新卡、进台账，还是写明不处理的理由。

## 结论三档

- **通过**：走合并流水线
- **修完再合并**：写审查意见，派回原执行者，在原分支上追加提交
- **退回重做**：方向错了。写清楚为什么，必要时改卡再派

## 合并流水线（通过时一口气做完）

```bash
git -C <主仓> merge --no-ff t/NNN-<slug> -m "merge T-NNN: <一句话 + 关键验收数字>"
<在 main 上跑全量测试>                         # 红了就立刻修或回滚，main 永远是绿的
git -C <主仓> push                             # 推完跑 git status -sb，确认不显示 ahead
```

然后同步文档，单独提交一次，提交信息写 `docs(plan): T-NNN 合并`：
- `status.md`：标已合并，写上合并 commit 和一句审查要点（带关键数字，让后来的人知道验证过什么）
- `tasks.md`：卡片列标为已完成
- 交接文档：更新当前状态、已完成、测试数
- 根 README 目录树、ADR、台账：按变更说明的「文档影响」逐条落实

最后运行 `scripts/wt.sh rm <卡号>`。分支没合并或有未提交改动时，它会拒绝删除。

- **冲突、迁移多 head**：由总指挥解决（重排 `down_revision`），不退给执行者。
- **分支起点是另一个未合并的分支**：先更新到上游的最终版本，复跑验收，再合并。

## 返工

1. 写 `docs/plan/reviews/<卡号>-rN.md`，模板是 `templates/review.md`，内容包括：
   - **结论**：一句话说清原交付哪里是对的、问题集中在哪
   - **必须修**：每条都写明位置、复现（输入，实际结果和应有结果）、修法
   - **应修**：用表格列；本卡不改的，写明交给哪张卡
   - **不做 / 回报要求**：追加提交用什么提交信息，要附哪些输出，不许削弱已有断言
2. 派回**原执行者**，在原分支上返工（返工口令见 `references/dispatch.md`）；看板标「返工」。
3. 同一执行者在同一问题上失败两次：换人、换模型，或者由总指挥接手。

## 独立审查

**什么时候用**：总指挥亲自写的卡、风险特别高的合并、你审完仍然拿不准的卡。

**怎么做**：
1. 另起一个 agent，可以是子代理，也可以是另一个执行者。**只给它规格（卡和相关 ADR）以及代码或分支**，不给你的结论，也不给你的猜测。
2. 要求它：每条必须修都实测复现，给出应修建议，最后给结论。
3. 你逐条决定采纳还是驳回，把理由写进变更说明或审查意见。

源项目里，独立审查两次都抓到了真问题：幂等比对漏掉了业务字段；CSRF 遇到非 ASCII 返回 500；读表单把请求体吃掉了。
