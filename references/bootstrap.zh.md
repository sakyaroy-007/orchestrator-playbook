# 开局与会话清单

授权和命令见[生命周期](lifecycle.zh.md)，四组设置问题见[配置](configuration.zh.md)。开局文件在运行时初始化成功后建立，不能靠写文件任命 holder。

## 检查已有或新项目

先做只读发现、读项目规则，记录真实 Git HEAD/分支/worktree、dirty/未跟踪状态，或非 Git 基线描述。提问前读现有计划和已定决定。证据分清已观察事实、未核实自报和缺口。

按拟做改动与项目策略选择起始检查：

- 获准后跑相关基线测试/构建/冒烟，记录精确命令、cwd、退出状态和实际输出。失败基线保持可见。
- 测试共享状态、准备并行或发现依赖迹象时，再检查隔离/顺序。按证据对受影响测试单跑或逆序/随机跑，不要求每个项目所有测试所有顺序全跑。
- 检查相关信任边界和事务边界。检查凭据路径是否忽略，不打印其值、不导出可能含秘密的历史。
- 区分 CLI 发现、已验证适配能力、登录就绪。能力建议不等于观察事实。

计划体检分“保留”和“缺口”，各带证据位置与建议归属卡。未跑检查列为缺口，不算通过。

## 只创建或补齐缺失基座

`init` 成功后，计划、员工规则、任务卡和交接采用规范化配置的 `paths`。旧项目接入先指出复用文件和既有约定冲突。保留原 README、AGENTS、计划、交接和源码。已有内容需要改变时，列为有范围的后续工作，不隐式替换。

Git、非 Git 以及自定义路径都使用随包基座助手。默认 `minimal`：真实项目根 README、配置的计划／员工规则／交接文件、首卡草稿和必要运行时副本；`standard` 再按需增加看板、决策和审查资源。文件数量不代表项目已经就绪。

```bash
python3 -I "$PLAYBOOK_SKILL_DIR/scripts/playbook-foundation.py" check --project "$PLAYBOOK_PROJECT" --profile minimal
```

报告新建／保留／冲突清单，包括不同版本的已有助手。想在现有 Git 仓库内建立独立子项目时，不能静默将上层仓库当成目标；apply 前解决路径意图。显式 start 或用户要求补齐文件时，使用本会话保存的身份与 epoch：

```bash
python3 -I "$PLAYBOOK_SKILL_DIR/scripts/playbook-foundation.py" apply --project "$PLAYBOOK_PROJECT" --profile minimal --session "$PLAYBOOK_SESSION" --epoch "$PLAYBOOK_EPOCH"
```

apply 通过运行时 scaffold guard 检查当前所有权与 active 状态，预检目标后只创建缺失文件。预览之后出现的文件也不覆盖。符号链接逃逸、目标冲突会阻止写入。运行时来源／摘要清单用于诊断，不授权升级已有副本。不能手工设置防递归标记。显式 start／补齐所需元数据不重复询问权限，也不授予派发、安装依赖或 Git 操作权限。

总入口的“检查协作文件”和“补齐缺失文件”复用同一 check／apply 流程。check 只读、不任命会话；未初始化项目先开始／接入。paused、prepared 或其他 owner 的项目先按生命周期处理，再写入。旧 `init-plan.sh --dry-run` 和只创建缺失文件的路径保留，供 legacy／默认 Git 布局使用；接入时不用 `--agents-md` 重写规则。

生成的首卡仍是草稿。填写真实目标、验收标准、内容范围、依赖、独占资源、实际命令、当前基线、策略引用及回报位置。明确轻量检查由实现员工执行，重型／共享检查由总指挥在 dispatch 结束后排程 verify。登记完整结构化 spec，再检查 readiness。未知命令、未解决占位符属于阻塞，不编造通过结果清空它们。

已配置项目的 `wt.sh new` 只在 guard 内创建 worktree；可执行的 `scripts/wt-setup.sh` 会报告 `setup pending`。guard 返回后按[派发参考](dispatch.zh.md)执行已批准的准备流程，避免嵌套受管 run，验证完成再派正文。开局不默认安装依赖或起服务。

## 规划首个有用任务

- 写简短目标/完成定义和明确边界，复用配置计划路径与现有决定。
- 只对跨卡选择写 ADR，必要时记录协作/分支策略，不覆盖 config。
- 保留一行一项待办，只按当前代码展开接下来可做的卡，写契约与验收，见[任务卡](cards.zh.md)。
- 只有协作地基确实阻塞安全推进时才先做它。已有失败测试记录原因与处置，不虚称基线全绿，也不盲目叠加依赖它的工作。
- 非 Git 项目只做一个活动操作并用本地快照，不编造分支/worktree 步骤。总指挥可以实施有边界的任务，按影响和策略选择审查。

## 恢复、接任与收工

resume 只给同一占任会话；takeover 按已准备交接或明确恢复处理。读配置交接、看板、台账和员工规则，再与运行时 `status`/`doctor` 比较。新派发前查孤儿和在途成果，不因新会话开始就起服务或重跑测试。

仍是 owner 时收工：

- 看板逐行与实际尝试、提交、dirty、日志和验收证据核对。
- 记录基线、配置 revision、绝对日期、下一步、未决决定和已知后台进程。
- 提交/推送/保留遵循项目策略，允许有记录的未推成果。
- 保护 dirty/未合并/运行中/未知/承载证据的 worktree，清理需单独检查和授权。
- 按需通过运行时 checkpoint、pause 或 handoff；交接 prepared 后不再改共享文件。
